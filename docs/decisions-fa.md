# دفتر تصمیم‌های محصول و توسعه

مرجع راهنما: [فهرست مستندات](README.md). تاریخ ثبت: ۲۰۲۶-۱۰-۲۷.

## تصمیم‌های تأییدشده کاربر

این تصمیم‌ها هدف توسعه‌اند؛ پیاده‌سازی‌شدن آن‌ها از این جدول نتیجه نمی‌شود.

| شناسه | تصمیم | دلیل و محدودیت | محل اثر |
|---|---|---|---|
| D-01 | افزونه عمومی برای فروشگاه‌های فارسی، با امکان عرضه انگلیسی | تجربه فارسی اولویت اصلی؛ افزونه اختصاصی یک فروشگاه نیست | PRD و UX |
| D-02 | نسخه اولیه: هسته قواعد، مدیریت فارسی کامل، آزمایش قانون و تنظیم نمایش | بخش تعویق بلوک/شورت‌کد در پاسخ اول، بعداً با D-08 جایگزین شد؛ بقیه دامنه معتبر است | FR-01 تا FR-10؛ M1 تا M4 |
| D-03 | فقط یک قانون برنده: دسته مستقیم، نزدیک‌ترین والد، اولویت قابل‌تنظیم، سپس ID صعودی | اولویت فقط در سطح specificity برابر اثر دارد؛ ترکیب قواعد مجاز نیست | FR-03؛ B-11 |
| D-04 | مقصد حذف‌شده: عبور به قانون بعدی؛ مقصد معتبر ولی خالی: مخفی‌کردن بخش و توضیح برای مدیر | fallback ساختاری با fallback بازاریابی متفاوت است | FR-04؛ B-12 |
| D-05 | فقط محصول ساده و متغیرِ قابل‌خرید؛ backorder پیش‌فرض خاموش و قابل‌فعال‌سازی؛ خارجی و گروهی خارج از نسخه اول | QA محدود و وعده تحویل روشن | FR-05؛ B-13 |
| D-06 | uninstall پیش‌فرض داده را حفظ کند؛ پاک‌سازی فقط با انتخاب صریح مدیر پیش از حذف؛ سفارش‌ها هرگز حذف نشوند | جلوگیری از از‌دست‌رفتن ناخواسته داده | FR-09؛ B-32 |
| D-07 | رابط فارسی/انگلیسی؛ یکپارچه‌سازی محتوای WPML/Polylang در مرحله بعد | بخش محدودیت به قالب کلاسیک با پاسخ اصلاحی کاربر و D-08 جایگزین شد | NFR-04؛ B-30 |
| D-08 | نسخه اول: شورت‌کد و بلوک پویا، قابل‌استفاده در ابزارک‌ها و صفحه‌ساز از طریق شورت‌کد؛ نمایش خودکار اختیاری؛ ابزارک اختصاصی ساخته نشود | کاربر صریحاً وابستگی به قالب خاص و پاسخ‌های قبلی محدودکننده را اصلاح کرد؛ یک renderer مشترک و QA چندبستری، بدون ادعای اثبات‌نشده همه قالب‌ها | FR-08/FR-10؛ B-22/B-30 |
| D-09 | ZIP برای پایلوت محدود؛ انتخاب مارکت و مدل تجاری پس از پایلوت | آماده‌سازی بسته، مجوز فروش یا انتشار عمومی نیست | M4؛ O-04 |

منبع D-01 پاسخ کاربر در بررسی اولیه محصول است. D-02 تا D-07 پاسخ‌های گزینه‌ای همین مرحله مستندسازی‌اند؛ D-08 پاسخ اصلاحی کاربر و تأیید گزینه شورت‌کد/بلوک، و D-09 پاسخ مسیر انتشار است. تغییر D-08 صریحاً بخش‌های متعارض پاسخ‌های پیشین را جایگزین می‌کند.

## انتخاب‌های عادی مهندسی

| شناسه | انتخاب | دلیل و مرز |
|---|---|---|
| E-01 | حفظ PHP، معماری کلاس‌های فعلی، CPT و post meta؛ بدون SPA یا جدول اختصاصی در این دامنه | مالک‌های موجود کافی‌اند؛ تغییر ذخیره‌سازی فقط با شواهد benchmark و تصمیم جدید |
| E-02 | برای اولویت پیشنهادی، عدد صحیح ۰ تا ۱۰۰، پیش‌فرض ۰، عدد بزرگ‌تر مقدم | در نبود مقدار، قواعد قدیمی ترتیب ID را حفظ می‌کنند؛ قرارداد آینده است |
| E-03 | حفظ بازه تعداد ۱ تا ۶ و مقدار پیش‌فرض ۳، و سه روش مرتب‌سازی فعلی | پاسخ در کد موجود است؛ بازتعریف محصول لازم نیست |
| E-04 | قیمت و واحد پول از WooCommerce؛ تاریخ ذخیره‌شده از WordPress؛ بدون تبدیل عمومی ارقام یا تقویم | جلوگیری از تبدیل مالی دوباره و شکستن متن ترکیبی؛ جزئیات در UX |
| E-05 | منبع ترجمه gettext با domain فعلی؛ فایل‌های UTF-8 فارسی و پیوندهای نسبی | مناسب ساختار موجود و قابل‌انتقال بین checkoutها |
| E-06 | ذخیره نامعتبر، آخرین پیکربندی سالم قانون موجود را حفظ کند؛ قانون جدید نامعتبر فعال نشود | جلوگیری از قطع ناخواسته پیشنهاد؛ تغییر هدف باید با تست مسیر واقعی ذخیره WP اثبات شود |
| E-07 | اولویتِ بدون meta با پیش‌فرض خوانده شود؛ پاک‌سازی داده قدیمی و migration گسترده لازم نیست | برای تنظیمات جدید version و default تعریف شود؛ داده واقعی در این مرحله تغییر نمی‌کند |
| E-08 | تصمیم تاریخی مرحله مستندسازی: اجرا در workspace فعلی، بدون worktree، commit، تغییر وابستگی یا اسکریپت اجرایی جدید | با درخواست صریح بعدی کاربر در ۲۰۲۶-۱۰-۲۷ برای اجرای M0 تا M4، QA محلی، commit و push جایگزین شد؛ دیگر محدودیت جاری نیست. داده/هاست واقعی، انتشار عمومی و ارسال ZIP همچنان خارج از اجازه‌اند |
| E-09 | TDD اجباری تعریف نشود؛ در اجرای آینده regression متناسب با قرارداد و رفتار واقعی | درخواست صریح چرخه strict TDD وجود ندارد؛ هیچ تست موجود حذف نمی‌شود |
| E-10 | نصب تازه در حالت manual؛ ارتقای نصب موجود در automatic/after_summary؛ فقط اولین خروجی موفق برای هر محصول در request | جای‌گذاری به انتخاب کاربر، حفظ رفتار قدیمی و مهار duplicate؛ جزئیات و آزمون چند embed در معماری |
| E-11 | جست‌وجوی matcher صفحه‌بندی‌شده با سقف ایمنی ۵۰۰ نامزد؛ تشخیص رسیدن به سقف به‌جای fallback خاموش | سقف از واکشی نامحدود جلوگیری می‌کند؛ رسیدن به آن در preview گزارش می‌شود و نیازمند بازبینی مدیر است |
| E-12 | engine پیشنهادها در صفحه‌های حداکثر ۲۴ محصول جست‌وجو می‌کند و مجموع کاندیدای بررسی‌شده برای یک پاسخ از ۵۰۰ عبور نمی‌کند؛ نتایج ناقص با سقف‌شدن بی‌صدا به‌عنوان تضمین ظرفیت کامل معرفی نمی‌شوند | جلوگیری از اسکن/واکشی نامحدود؛ benchmark مقیاس اجرا شده و به‌عنوان مشاهده ثبت است؛ سقف و کارایی در گیت محلی E-15 سنجیده شده‌اند |
| E-13 | engine برای هر فراخوانی `recommend()` مجموعاً حداکثر ۵۰۰ variation candidate را در صفحه‌های حداکثر ۲۴تایی بررسی می‌کند؛ این سقف مستقل از بودجه ۵۰۰ محصول E-12 است. تعداد بررسی‌شده و رسیدن به سقف diagnostic دارد و preview مدیریت درباره احتمال حذف variable product هشدار می‌دهد | محدودکردن هزینهٔ variationهای متغیر با آشکارکردن نتیجهٔ احتمالی ناقص؛ regression مصنوعی ۵۰۱ variation در integration performance با اجرای کامل suite پاس شد؛ variable stress و matrix benchmark اجرا شده‌اند؛ کارایی محلی در E-15 سنجیده شده است |
| E-14 | timestamp فایل‌های داخل ZIP روی زمان ثابت قرار می‌گیرد تا ورودی یکسان با lock یکسان، ZIP باینری تکرارپذیر بسازد؛ زمان واقعی build در manifest بیرونی ثبت می‌شود | قابل‌مقایسه‌بودن hash و اطمینان از اینکه آزمون M4 روی همان artifact نهایی است؛ باید با دو build متوالی و hash برابر اثبات شود |
| E-15 | پس از ثبت benchmark ماتریس کامل، برای NFR-02 یک گیت مهندسی محدود به محیط اندازه‌گیری‌شده تعریف می‌شود: matcher p95 سرد/گرم ≤125/10ms؛ recommendation ordered/random برای 1k ≤125/50 و ≤250/125ms، 10k ≤200/75 و ≤550/150ms، 50k ≤750/75 و ≤1200/600ms؛ حافظهٔ peak ≤120MiB. سرد یعنی WP object cache flush شده و DB buffer pool همچنان warm است. | آستانه‌ها انتخاب مهندسی محلی برای این محیط‌اند، نه تأیید کاربر و نه SLA عمومی/محصولی؛ نتایج benchmark مشاهده‌های محلی‌اند. variable-heavy stress پنج‌نمونه‌ای خارج از گیت پذیرش است. جزئیات و نتیجه‌ها در گزارش QA/B-31 ثبت‌اند. |

## پیشنهادهای تأییدنشده

- آمار تبدیل، تخفیف گروهی، یادگیری سفارش و انتخاب variation درجا صرفاً گزینه مراحل بعدند.
- benchmark و گیت محدود محلی NFR-02 در E-15 تعریف و سنجیده شده‌اند؛ این گیت جای SLA عمومی/محصولی را نمی‌گیرد و به کاربر تأیید یا تعهدی نسبت نمی‌دهد.
- بلوک و شورت‌کد طبق D-08 داخل MVP هستند؛ فقط چندزبانه‌سازی دسته‌ها و اتصال اختصاصی WPML/Polylang نیازمند تصمیم مرحله بعد است.
